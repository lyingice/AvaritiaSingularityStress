## A. 动能机器（纯模型，无 BER、无 visual）—— 最大缺口

| 方块 | 方块类 | 方块实体 | 渲染链路 | 模型来源 |
| --- | --- | --- | --- | --- |
| kinetic_neutron_collector | `KineticNeutronCollectorBlock` (`HorizontalKineticBlock`) | `KineticNeutronCollectorBlockEntity` (`KineticBlockEntity`) | **只有 blockstate 静态模型** | `block/machine/collector/…`（datagen） |
| dense_ / elite_ / ultimate_ 同上 3 个 | 同上（同一 BE） | — | 同上 | 同上 |
| kinetic_neutron_compressor | `KineticNeutronCompressorBlock` (`HorizontalKineticBlock`) | `KineticNeutronCompressorBlockEntity` (`KineticBlockEntity`) | **只有静态模型** | `block/machine/compressor/…`（datagen） |
| dense_ / elite_ / ultimate_ 同上 3 个 | 同上 | — | 同上 | 同上 |

> 结论：8 个方块、2 个 BE，**没有任何旋转部件**。它们全是 `HorizontalKineticBlock` + `KineticBlockEntity`，
> 也就是说"能接动能但没有轴、没有转动视觉"。要加转动 = 先注册 visual（`OrientedRotatingVisual`/`SingleAxisRotatingVisual`），
> BER 在这里没用（`KineticBlockEntityRenderer` 会早退，见 T17）。
> 注意 `render_type` 是 `minecraft:cutout`，模型是 datagen 产物（改模型要改 provider，不是改 json）。

## F. 缺口清单（可直接变成任务）

1. **8 个动能机器（collector/compressor）没有任何旋转视觉** —— 想"像动能方块"就得加 visual；现在接上轴也只有静态模型。
2. **3 个 BER 是死代码**：2 个应力传输器 + 稳定器（都是 `KineticBlockEntityRenderer` 子类且已注册 visual）。留着只为"可视化关闭"兜底，注释要写明，否则下次又要查一遍 T17。
3. **2 个 crafter 是双层风险**：BER 与 visual 同时开，`skipVanillaRender=false`；一旦出现"一层不转"就是 T11。
4. **应力传输器的轴朝向**：`OrientedRotatingVisual.of()` 写死 `to=FACING`，而 `hasShaftTowards` 认 `FACING.getOpposite()`（T18）——输入端"没轴"的根因。
5. **12 个方块的模型是 datagen 产物**：手改 json 会被下一次 `runData` 覆盖（T03 的同源问题）。

## G. 给预设改进的直接结论

一个"方块"在本工程要碰 5 处才算完整：`Block` 类 / `BlockEntity` 类 / `ModBlocks`+`ModBlockEntities` 注册 / 资源（datagen 或手写）/ 客户端（`ModRenderers` 与 `ModVisualizers` 二选一或都选）。
本次失败案例的根因不是"不会写"，而是**第 5 步选错了层**（选了 BER 而 Flywheel 会早退），且预设里没有一条"先判断该走 BER 还是 visual"的判定规则——这条应作为改造重点。
