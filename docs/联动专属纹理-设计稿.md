# B16 动能联动专属纹理（设计稿 + 排错表）

> 目标：本模组的机器（默认：四档收集器、四档压缩机）与 Create 的**传动杆 / 小齿轮 / 大齿轮**相邻时，
> 那颗轴/齿轮改用本模组的专属纹理渲染；拆掉机器或离开后自动恢复 Create 原纹理。

## 1 结论先行（实现分三层）

| 层 | 位置 | 作用 |
|---|---|---|
| 资源 | `textures/block/neutron_link/*.png`、`models/block/neutron_link/*.json` | Create 轴/齿轮模型的"换纹理副本"（R1：原样复制，不改图像） |
| 触发名单 | `data/avaritia_singularity_stress/tags/block/neutron_link_sources.json` | 哪些机器算"联动源"（四档收集器 / 四档压缩机 / 空间折跃隧道）；用数据包可改，不必重编译 |
| 客户端视觉 | `init/client/visual/NeutronLinkVisual.java` + `init/client/visualizer/ModVisualizers.java` | 接管 Create 的传动杆视觉，按邻居切换两套 instance；**齿轮交回 Create 原样**（用户定稿：不改齿轮） |

## 2 为什么必须"整体接管 Create 的一个 visualizer"

Create 6.0.10 的 `AllBlockEntityTypes` 里**没有** SHAFT / COGWHEEL 字段，三者共用一个方块实体类型：

```java
// allapis/Create-mc1.21.1-dev/.../AllBlockEntityTypes.java:254-259
public static final BlockEntityEntry<BracketedKineticBlockEntity> BRACKETED_KINETIC = REGISTRATE
    .blockEntity("simple_kinetic", BracketedKineticBlockEntity::new)
    .visual(() -> BracketedKineticBlockEntityVisual::create, false)   // ← 第二个参数 false = skipVanillaRender 恒 true
    .validBlocks(AllBlocks.SHAFT, AllBlocks.COGWHEEL, AllBlocks.LARGE_COGWHEEL)
```

- 一个 `BlockEntityType` 只能挂一个 `BlockEntityVisualizer`，所以"只给齿轮换"做不到；
  只能在 factory 里按 blockState 分流——Create 自己也是这么干的
  （`BracketedKineticBlockEntityVisual.java:21-33`：大齿轮 → `LargeCogVisual`；小齿轮 → `COGWHEEL`；其余 → `SHAFT`）。
- 6.0.10 的 `BracketedKineticBlockEntityVisual.create(...)` 字节码与 6.0.11 源码逐语句一致（javap 已核）。
- `LargeCogVisual` 的构造器是 `private`，**不能继承**；大齿轮要自己拼两个实例
  （`SHAFTLESS_LARGE_COGWHEEL` + `COGWHEEL_SHAFT`），代码照 `BracketedKineticBlockEntityVisual.java:42-53` 写。

## 3 为什么用"两套 instance + setVisible"，而不是邻居变了就重建

- `VisualizerRegistry.setVisualizer` 是**无条件覆盖**（Flywheel 1.0.6 的 `VisualizerRegistryImpl` →
  `BlockEntityTypeMixin.flywheel$setVisualizer` 里是 `putfield`，没有拒绝重复注册的分支）。
- visualizer 是**懒读取**的：`BlockEntityStorage.createRaw` 在每次 `queueAdd` 时才去取，所以注册晚也没关系。
- `VisualManager.queueUpdate(T)` 只回调 `Visual.update(float)`，**不会重建 visual**
  （反汇编：`Storage.update` 里 visual 为 null 直接 return，非 null 时只调 `update`）。
  所以"邻居变化 → 换模型"没有官方轻量通道。
- `Instance.setVisible(boolean)` 是 Flywheel 专为此留的 default 方法（转发到 `InstanceHandle.setVisible`），
  切换不动 instance 生命周期。轴的实例只有 6 个面，多备一份隐藏实例的代价可以接受。

## 4 注册时机：必须晚于 Create

Create 的注册发生在 `FMLClientSetupEvent` 的监听器里（`CreateBlockEntityBuilder.registerVisualizer()`，
6.0.10 字节码与 `CreateBlockEntityBuilder.java:105-116` 一致）。
`FMLClientSetupEvent` 是并行派发事件，跨 mod 的 `enqueueWork` 顺序无保证，
所以本模组把**全部视觉注册**挪到了 `FMLLoadCompleteEvent`（`ModClientEvents.loadComplete`）。
注册是幂等的，重复调用无害。

## 5 坐标系与上下文（三个易错点）

1. `setPosition(getVisualPosition())` 用的是**相对 `VisualizationContext.renderOrigin()`** 的视觉坐标；
   大齿轮齿相位偏移 `BracketedKineticBlockEntityRenderer.getShaftAngleOffset(axis, pos)` 必须用**世界坐标 `pos`**
   （Create 的 `LargeCogVisual` 同样传 `pos`，见 `BracketedKineticBlockEntityVisual.java:51`）。
2. 对比结构（contraption）里走的是**同一个 visualizer**
   （`ContraptionVisual.java:150-167` 调 `VisualizerRegistry.getVisualizer(be.getType()).createVisual(...)`），
   此时 `be.getLevel()` 是 `VirtualRenderWorld`，读到的是被搬走的方块集合。
   本模组的判定因此"方块一起被搬走 → 联动外观也一起走"，与直觉一致。
3. `skipVanillaRender` 必须恒 `true`（Create 原本就是）。若返回 false，Create 的 BER 会和 Flywheel 实例叠画。

## 7 排错表（本项目已踩过的坑）

| 症状 | 原因 | 修法 |
|---|---|---|
| 看起来“完全没变化” | 第一轮占位用的就是 Create 原图，换与不换长得一样 | 换占位纹理（见 §6）；或看日志 `[neutron_link] ...` 判断判定是否命中 |
| 齿轮/轴整块消失 | 我们接管后 `skipVanillaRender` 没恒返回 true，或 visual 工厂抛异常（模型路径写错） | 先看日志有无 partial model 烘焙报错；确认 `skipVanillaRender(be -> true)` |
| 纹理没变 | visualizer 被 Create 后注册覆盖（顺序反了） | 注册放 `FMLLoadCompleteEvent`；用 `VisualizerRegistry.getVisualizer` 身份比对排查 |
| 拆掉机器后纹理不变 | 邻居变化没有通知 Flywheel | 本实现靠 visual 的 `tick` 每帧复核（6 次 blockState 查询），改判定逻辑别删掉 tick |
| 大齿轮齿相位错位 | 用了 `getVisualPosition()` 当 `getShaftAngleOffset` 的坐标 | 必须传世界坐标 `pos` |
| 编译报 `void 无法转换为 RotatingInstance` | `Instance.setChanged()` 返回 `void`（`AbstractInstance` 是 `final void`），不能挂在链式返回里 | 先拿到 instance，再单独 `instance.setChanged()` |
| 构建被 `neoforge-21.1.232.jar is locked by ... Minecraft ...` 挡住 | 游戏客户端正在运行，映射着 `build/moddev/artifacts/*.jar` | 关掉客户端再 `gradlew compileJava --offline` |

### 原版机制（为什么不能照搬传动杆的做法）

| 层 | Create 6.0.10 的实现 |
|---|---|
| 数据 | `BeltBlock.CASING`（布尔 blockstate，`BeltBlock.java:102`）+ `BeltBlockEntity.casing` 枚举 `NONE/ANDESITE/BRASS`（`BeltBlockEntity.java:64,74`），NBT 键 `"Casing"`（`:213`） |
| 交互 | 扳手右键 → `setCasingType(BRASS/ANDESITE/NONE)`（`BeltBlock.java:315,327,350`） |
| 渲染 | **方块模型**：`BeltGenerator` 按 `CASING` 选 `block/belt_casing/*`（`BeltGenerator.java:65`），`BeltModel` 用 `CASING_PROPERTY` 决定几何（`BeltModel.java:26,39-55`）；Flywheel 的 `BeltVisual` 只画皮带/滚轮（`AllBlockEntityTypes.java:449-452`） |

关键：机壳模型是**按 blockstate 全局烘焙**的，不随邻居变；所以"按位置换机壳纹理"在模型层做不到。
但正因为它是模型（不是实例），我们只要保证 vanilla 的 `casing == NONE`，在 Flywheel 里**叠一层**就不会叠影。

### 曾实现过的内容（现已删除）

- 视觉：`init/client/visual/NeutronBeltVisual.java`，`extends BeltVisual`（public 类 + public 构造，
  保留 Create 的皮带/滚轮滚动逻辑），额外挂一个静态 `RotatingInstance`：
  `setRotationalSpeed(0)` + 模型 `neutron_link/belt_casing` + `setPosition(getVisualPosition())`。
- 注册：`ModVisualizers` 覆盖 `AllBlockEntityTypes.BELT`，`skipVanillaRender(be -> !be.shouldRenderNormally())`
  ——必须保留 Create 原语义，不能恒 true。
- 几何：复制 `create:block/belt_casing/horizontal_middle`（`[0,0,0]→[16,11,16]`，罩住皮带下方），
  纹理换成 `neutron_link/belt_casing`；占位直接复制 `create:block/belt/brass_belt_casing`（**64×64**）。
- 范围：只处理水平段（`SLOPE == HORIZONTAL`），斜段/竖直段的机壳是另几套模型，先不做以免穿模。
- 判定：与传动杆共用 `NeutronLinkSupport.isLinked(...)`（六邻任意一面贴名单方块）。

删除清单：`NeutronBeltVisual.java`、`ModVisualizers` 里的 BELT 覆盖块、`ModPartialModels.NEUTRON_LINK_BELT_CASING`、
`models/block/neutron_link/belt_casing.json`、`textures/block/neutron_link/belt_casing.png`。
（`NeutronLinkSupport` 保留——传动杆视觉仍在使用。）

## 9 B17 中子传动杆（继承 Create 轴类的新方块）

用户定稿：传动杆模型固定、不能按 blockstate 换，那就**继承 Create 的轴类、自己造模型**，做一支"中子传动杆"。

### 与 B16 的区别（两套机制并存）

- **B16 自动切换**：Create 原有传动杆，贴着名单方块时换成 `neutron_link` 纹理；拆掉就恢复。
- **B17 中子传动杆**：玩家主动放置的新方块，放在哪都是中子外观，不做邻居判定。

### 已知限制（待实机确认）
